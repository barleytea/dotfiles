# 技術文書・README・開発者向け説明

- 技術用語、API名、関数名、ファイル名、識別子は正確に保つ。
- 専門用語を不必要に日常語へ言い換えない。くだくと、書き手が分かっていないように見える（×相手が生きているか → ○受信側の稼働状況）。
- 開発者への報告では、PR、マージ、main、デプロイをそのまま使う（mainにマージしました）。
- 何が起きたか、何が原因か、どう対処するかを区別する。
- 分からない仕様は書かない。TODOか空欄にして、何が分かれば書けるかを添える（×「有効期限は設定項目で指定します」と推測で書く）。
- システムやテストを人のように描写する比喩は、定着した表現以外は避ける（テストが転ぶ、ログを吐く、静かに壊れる）。何がどうなったかを書く。データ・値・システムの動詞は `register.md` にある。
- 英語の言い回しを1語ずつ訳さない（端のケース → 例外的な場合）。
- 定着した技術用語を和語に言い換えない（ペア、キー、エントリ）。依頼文がくだいた言い方をしていても、技術文ではその分野の用語で書く（×組にして保存する → ○ペアで保存する）。
- 技術ブログは、事実を1文ずつ素直に置く。強調のための言い回し（〜までは、〜さえ、〜ところです）や、段落ごとの小さな結論を足さない。
- 技術ブログの導入は、書き手の近況や動機から、そのまま本題に入る。「さて、本題です」のような切り替えの文を挟まない。作った明るさ（〜するぞ！）を足さない。
- くだけた調子の記事でも、「（笑）」「〜んですね」「〜ですけどね！」で軽さを作らない。事実を普通に書けば、内容の面白さは伝わる。
- 「ここからは、〜を説明します」のような橋渡しの文を挟まない。見出しか改行で次へ進む。
- 「〜のです」「〜のでしょうか」で読み手に語りかけない。「〜ません」「〜でしょうか」と素直に書く。
- その分野で普通に使う言い方を選ぶ（×全体を紹介します → ○全体像を紹介します）。
- 手順は実行順に並べ、1項目に複数の操作を詰め込みすぎない。元の手順が渡されていない時は、一般的な手順を仮に作らない。書き方の枠だけを示し、手順そのものは空欄にする。
- 前提条件、対象バージョン、制約、破壊的変更を明記する。
- PRや報告は「背景・変更内容・テスト」のように見出しで分ける。コメントやコミットは、そのリポジトリの言語と書き方に合わせ、何をしたかより、なぜそうしたかを書く。
- 開発者以外に説明する場合は、内部実装よりユーザーに起きる変化を中心に書く。ファイル名や関数名は出さない。言い直すと別の物を指してしまう語（ドメインとメールアドレス、ログインとアカウント登録）は、言い換えずにそのまま使い、必要なら短い説明を添える。敬語の高さは元の文書に合わせて保つ（お客様宛てのメールの「ございます」「いただけますでしょうか」を下げない）。社内の呼び方（ユーザー様、操作を行われた）も、お客様、操作をされた、のような普通の言い方にする。専門語を外す時も、原因などの情報は消さず、普通の言葉で言い直して残す（×APIサーバーの負荷上昇によるレイテンシの悪化 → ○サーバーに負荷がかかり、処理が遅くなったため）。

## 意味を守る
技術文書では、読みやすさより先に意味を守る。直す前に次の6つを原文から拾い、直した後に1つずつ照らす。1つでも変わった所は、原文の言い方に戻す。
- 否定・例外・条件（〜しない、〜を除く、〜の場合に限り、以上と超える、以下と未満）
- 数値・単位・範囲・既定値
- 義務の強さ（必須・推奨・任意、しなければならない・すべき・してもよい）。上げも下げもしない。「必須ではない（任意）」と「不要」、「〜する必要があります」と「〜をお願いします」は別の強さ。誰がするか（各自で、利用者が）も落とさない。
- 主体（誰が、何が実行するか。クライアントが送る、サーバーが返す）
- 確かさ（確認済み・推定・調査中・可能性がある）。「確認されていない」を「無い」に、「推定」を「原因」に変えない。
- 識別子とコード（API名、設定キー、コマンド、エラーメッセージ、コードブロックの中）。一字も変えない。

## 構造で読みやすくする
言葉を言い換えるより、情報の順番と置き場所を直す方が効く。
- 読み手が最初に知りたいことを先に置く。READMEは何をするものか、最短の使い方、詳しい設定の順。障害報告は影響（誰に、いつから、今どうなっているか）、経緯、原因、対策の順。設計書は決めたこと、背景、比べた案、決めた理由の順。PRは変更の要約、理由、確認方法の順。
- 1段落に混ざった種類の違う情報（事実と推測、手順と注意、決定と今後の検討）を分ける。
- 文に埋まった仕様の値（パラメータ、型、必須か、既定値、範囲）は、表か箇条書きに出す。原文に無い値は作らない。
- 注意、制約、破壊的変更は、それが効く場所（手順の直前、項目の横）に置く。
- 1行目で、何の文書で、今どういう状態かが分かるようにする（障害報告なら「解消済み・原因は調査中」、PRなら「破壊的変更を含む」）。API仕様はエンドポイントを見出しにする。
- 見出しは中身と合わせる。見出しの範囲外の項目を入れない。見出しで言ったこと（必須、注意）を本文で繰り返さない。
- 「ラベル：値」の行にするのは、日時、場所、金額、バージョンのような短い値だけ。影響や原因のように文になる内容は、ラベルを付けずに文で書く。一般の人向けのお知らせは、値の行を最小限にして、文でつなぐ。
- 1つの結果に条件が2つ以上ある時は、「次のいずれかの場合に〜」と書いて、条件を箇条書きに分ける。
- 強さの違う指摘や依頼（必須、任意、今回は不要）が並ぶ時は、強さごとにまとめ、強さを見出しか項目の頭に書く。読み手が文の最後まで読まなくても強さが分かるようにする。
- 条件が3つ以上詰まった1文は分ける。ただし、どの条件がどの結果に掛かるかを崩さない。
- 論文や設計書の主張の強さ（示した、示唆される、傾向が見られた）は変えない。

## 直さないもの
- もう読める技術文は、そのまま返す。好みの言い換えで触らない。
- 専門用語、略語、英語のままの用語をくださない、訳さない（スループット、冪等、レイテンシ）。
- 既にある見出しの構成は作り替えない。足りない時だけ足す。
- 既に番号や見出しで整っている文書では、手順の順番や項目の置き場所を動かさない。上の「効く場所に置く」は、情報が1段落に混ざっている時に当てる。
- 頼まれていない削除をしない。消してよいのは、中身の無い前置きや飾りだけ（READMEの「〜を目指しています」「〜な世界を実現したい」のような理念の文も飾りに入る）。原因、条件、作者の呼びかけ（フィードバックを募る一文など）は、言い方を整えるだけで残す。

例（合成）：
- 前：本APIは、認証済みのリクエストに限り、1分あたり最大60回まで呼び出すことが可能となっております。
- 後：認証済みのリクエストだけが呼び出せます。上限は1分あたり60回です。
- 守ったもの：「認証済みに限る」という条件、「1分あたり」「最大60回」。崩したのは回りくどい言い方だけ。
